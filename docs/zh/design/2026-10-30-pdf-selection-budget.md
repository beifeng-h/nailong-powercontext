# PDF 页检索的相关性与报表覆盖

页级检索的返回上限同时约束普通正文、附注和独立报表。相关正文不能仅因其他报告存在足够多的报表标题而失去全部候选名额；明确请求报表时，也不能让堆积查询词的讨论段落代替实际报表。

旧选择流程先加入全部报表覆盖候选，再由全局相关排名补足剩余名额。五份报告分别包含两页利润表和两页现金流量表时，覆盖候选恰好占满二十个名额，即使普通附注是全局相关排名第一也不会返回。增加报告数可以触发该问题，无须改变问题、目标正文或相关性分数。三类报表会更早耗尽同一预算。

## 选择顺序

相关性计算、分词、词项扩展、文档字段、FTS 信号和报表识别保持原有规则。选择阶段形成两条顺序：全局相关性与多样性排序，以及按请求类别组织的报表覆盖顺序。

每轮先为每个尚未覆盖的请求类别取下一张报表，再从全局相关顺序取下一张未返回页面。跨类别页面在本轮同时满足其类别；已选页面在两条顺序中去重。循环至返回上限或两条顺序均耗尽。没有报表类别时使用全局相关顺序。

每轮覆盖的宽度取决于问题实际请求的报表类别，不按公司名称、报告数量或固定保留比例调整。小上限仍优先满足明确报表请求；有足够名额时，全局相关候选也持续获得位置，不会被任一报告集合无限挤出。

## 验证要求

新增公共接口回归分别使用两类和三类报表、五个不带公司名称的文档 ID。全部页面经过 Source 解析、真实 Runtime 持久化和重新打开，再查询普通附注与报表，逐条回查完整正文、来源、文档摘要和物理页码，核对返回上限与不同页要求。

保留已有小上限报表覆盖测试。独立原型中，单纯把全局相关候选放在最前会让讨论页占据 `limit=1`，因此不采用这种顺序。五份完整原 PDF、1258 页上的十六个人工开发问题用于检查原有支持页是否退步；这些问题已经参与开发，不能视为盲测。

正式评分不披露失败维度。候选名额耗尽是已复现的排序缺陷，不等于已经证明它是正式零分的唯一原因；完整解析质量与正式 Recall 门槛仍须由平台验证。

## 实际结果

2026-10-30，使用 Python 3.12.3 和官方固定 78 项依赖，在真实 Runtime 中复现旧选择器的两项新增回归失败；修复后，包含两项新增回归的 83 项 PDF 测试与六项公开 PDF 测试全部通过，无错误或跳过。

五份完整原 PDF 的 1258 个物理页全部持久化，并在重开后逐页核对精确正文、来源、摘要和引用。旧新选择器分别在单 CPU 进程中查询同一 scoped Memory，十六道人工诊断题均保留全部 23 个支持页，无逐题回退。人工题已参与开发；这些结果不代表正式质量评分或隐藏问题召回率。

原验证包保持不变，候选包前后逐文件 SHA256 校验通过，官方 78 项依赖前后匹配。验证使用单 CPU affinity 并记录进程 RSS，没有重现完整的 2 GiB、普通用户、离线和只读官方沙箱。未运行全库 lint/type 检查。
